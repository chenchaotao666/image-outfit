修改报告时，从 LLM提示词-加载索引.json 查看实际加载顺序和运行模式。跨模块共用的测量指标在「用户资料」注入一次，功能提示词直接引用该节。每个字段的判断与缺失条件由对应功能模块维护。Face++ 数据来源约定见「报告总则」，分项字段要求见「报告分项结构」。

例如调整照片明度或纯度时，在「色彩DNA/面部色彩属性」修改照片观察要求。调整输出字段时，同时更新「报告分项结构」、server/analysis/details.js 的校验、server/styling/color-assessment.js 的归档逻辑和报告页的取值。用 npm run inspect:prompts 查看最终提示词，用 npm test 核对有数据、部分缺失和旧报告。修改模型输入后同步更新加载索引版本。

眉型、发型等未启用规则仍为草案，文件归类不表示启用了这些规则。

文件命名约定
*-判断规则.json：检测输入、判断条件、证据要求及缺失处理。
*-推荐规则.json：命中条件、优先级、方案与依据。现有部分模块的 reason/advice 也是页面使用的文字，可直接修改。
*-界面文案.json：标题、按钮、结果名称和固定解读；不改变判断条件。
*-配色方案.json：颜色名称、色值、组合及搭配章节文案。
*-展示规则.json：页面结构、分类顺序、介绍与分组文案。
*-图片库.json：图片路径、标签、顺序、图片说明与来源。
*-LLM提示词.txt：输入变量、判断步骤、规则优先级、输出结构与边界。

维护流程
1. 修改源 JSON，保留稳定 ID、字段名及有效 JSON 格式。
2. 运行 npm run build:styling，同步评分、色彩、四季、衣橱配置到小程序。
3. 运行 npm run check，检查引用、素材和同步状态。
4. 在微信开发者工具中重新编译小程序。若修改服务端判断规则，重启服务并重新分析；已保存报告不会自动重算。
生成文件 miniprogram/utils/*-data.js 不要手工修改。
页面固定解读与本次照片观察是两类内容：固定解读由配置提供；具体观察与数值来自报告，不应伪造成固定检测结果。

LLM提示词入口：LLM提示词-加载索引.json。变量及引用配置见LLM提示词-变量定义.json；业务判断和输出边界直接写在对应提示词中。
运行 npm run inspect:prompts，在 docs/LLM提示词预览 查看最终提示词；示例使用虚构资料，不包含用户照片。
修改提示词后运行 npm run check 并重启服务，新报告才采用新提示词。改变评分档位语义时需更新评分version并重新分析；仅改权重或分数段会影响旧报告已有档位的展示计算。

图片库统一维护：将图片放入对应 miniprogram/assets 子目录，配置唯一id、src、enabled、排序/分类标签及source、rights。沿用同库现有记录的字段格式；不要把参考素材标为自有或授权素材。
四季图片用season、order、gender、colors；衣橱图片用group、order、gender、name、advice；色彩搭配图片用tags、gender、occasion、alt。
素材提取脚本会重建初始图片库，日常增图不需要运行。完成后统一执行 build:styling 和 check。

提示词统一引用语法
{{四季搭配-季节参考.json}}读取整份文件；{{四季搭配-季节参考.json.seasons}}读取seasons字段。
{{四季搭配-生成规则.json.modules.seasons.outputMode}}直接读取该字段，不计算或筛选。
文件名必须唯一，字段必须存在；错误引用会在加载时失败。
所有运行结果.*间接变量已移除；规则候选直接读取文件，由提示词明确适用条件。用户资料和检测变量仍取本次请求。
独立四季页使用季节参考、页面文案与展示规则、图片库；报告建议由LLM生成，独立页不直接展示details.outfits。

配色提示词直接引用：色彩类型分析-推荐规则.json、色彩类型分析-界面文案.json.results、色彩搭配指南-配色方案.json.palettes，结合skin.color选择。已移除“运行结果.推荐配色”变量及提示词生成时的color-guide调用。独立配色页面仍按同一套配置展示色板与固定解读，不会写回覆盖报告的模型输出。

风格DNA/风格解析：展示规则按本次报告个人风格index选择六套示范及解读；界面文案保存标题与按钮；图片库通过imageId引用素材。增加独立图片不需要region或位置参数，保留素材来源和权利说明。运行build:style-guide后刷新预览。该页使用已有报告，不额外调用LLM。
